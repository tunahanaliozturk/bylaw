## 0.5.0 - 2026-10-19

- Review fixes to the new providers: only a credential chain's errors become a note, and only for the cloud providers, so a bug can no longer pass `fail-on` as a note. A key variable set but empty is refused. The JSON fallback drops `<think>` blocks and reads the first JSON object that decodes, names only the schema's fields in its problems, treats an empty answer as no review, skips its retry when it would pass `[budget] pr_tokens`, and marks the brief for the prompt cache. Vertex AI errors are named by status, an `AZURE_OPENAI_ENDPOINT` copied with `/openai/v1` still works, the extra checks look for boto3 and requests, and an eval run against a local server records the server in its reviewer identity. docs/providers.md now covers Foundry's metadata egress to Anthropic and Ollama's small default context length (ADR 0018).
- [docs/providers.md](docs/providers.md) lists, for each model provider, where the brief goes, which variables it reads and which extra it needs, with links to each cloud's own data terms. The README and docs/privacy.md link to it, and ADR 0018 records why the providers work the way they do.
- Azure: `--provider foundry` reviews with Claude in Microsoft Foundry through the Anthropic SDK's Foundry client, with structured outputs, the resource from `ANTHROPIC_FOUNDRY_RESOURCE` and the key from `ANTHROPIC_FOUNDRY_API_KEY`. `--provider azure-openai --model <deployment>` reviews through Azure OpenAI's v1 API with the OpenAI SDK, structured outputs and `store: false`, the endpoint from `AZURE_OPENAI_ENDPOINT` and the key from `AZURE_OPENAI_API_KEY`. Without a key, both sign in with Microsoft Entra ID through `DefaultAzureCredential`, which needs `pip install 'bylaw[azure]'`. The OpenAI and Anthropic keys are never sent to Azure (ADR 0018).
- Google Vertex AI: `--provider vertex` reviews with Claude on Vertex AI through the Anthropic SDK's Vertex client, with structured outputs and `claude-opus-5-5` by default. It authenticates with Application Default Credentials (`gcloud auth application-default login`, `GOOGLE_APPLICATION_CREDENTIALS` or workload identity), which needs `pip install 'bylaw[vertex]'`, and reads the region from `CLOUD_ML_REGION` and the project from `ANTHROPIC_VERTEX_PROJECT_ID`. Vertex AI has no server-side fallback, so none is asked for. When a credential chain finds nothing or cannot refresh a token, the model review fails with a note that names the provider instead of stopping the run (ADR 0018).
- Amazon Bedrock: `--provider bedrock` reviews with Claude in Amazon Bedrock through the Anthropic SDK's Bedrock client, with `anthropic.claude-opus-5-5` by default. Credentials come from the AWS chain only: a Bedrock API key in `AWS_BEARER_TOKEN_BEDROCK`, or SigV4 signing with `AWS_ACCESS_KEY_ID`, a profile, SSO or a role, which needs `pip install 'bylaw[bedrock]'`; the region comes from `AWS_REGION`. That endpoint has no structured outputs, so the review uses the JSON fallback, and it has no server-side fallback, so none is asked for. `BYLAW_API_KEY` and the Anthropic key are never sent to AWS. The Action installs the extra when `provider` is `bedrock` (ADR 0018).
- Local models: `--provider openai-compatible --base-url http://localhost:11434/v1 --model qwen3:4b` reviews through any server that speaks the OpenAI Chat Completions API, such as Ollama, vLLM or LM Studio, and needs no key (the Action's `base-url` input). Plain `http://` is refused unless the server is on this machine, because the brief holds the pull request's code. bylaw asks for its review schema as a strict response format and also writes the schema into the prompt, because a local server may reject the format or accept it without enforcing it. The answer is checked against the schema either way; a wrong one goes back to the model once with what was wrong, by field path, and a second wrong answer fails the model review with a note that names the problems. A key for the server goes in `BYLAW_BASE_URL_KEY` (the Action's `base-url-api-key` input); `BYLAW_API_KEY`, `OPENAI_API_KEY`, `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` are never sent to it, and a set `OPENAI_CUSTOM_HEADERS`, whose headers the SDK would add, is refused. The same holds for Azure OpenAI, and `ANTHROPIC_CUSTOM_HEADERS` is refused for Foundry (ADR 0018).
- bylaw runs as a self-hosted GitHub App: one install for an organisation instead of a workflow file per repository. A webhook server, `bylaw-app`, checks each delivery's `X-Hub-Signature-256` before reading it, queues the review and answers at once; a worker runs the same review as `bylaw review --pr N --post` with an installation token for that one repository, with contents read only. A pull request has at most one review waiting, which reads the pull request as it is when it starts; the head it read counts as reviewed, so a delivery for a head already reviewed or waiting does nothing, and one pull request is never reviewed twice at the same time. The queue lives in memory: after a restart, the next push or a redelivery picks up what was missed. The server's dependencies (Starlette, Uvicorn, PyJWT) are the optional `app` extra, so the CLI and the Action install no web stack (ADR 0017).
- In the app, the installation's model key reviews only same-repository pull requests by owners, members and collaborators unless `.bylaw.toml` says otherwise: forks and other authors get bylaw's own checks and a summary note, as ADR 0006 does for the Action. `[app] model_review = "all"` opens it to everyone, and `[app] model_review_label` to one pull request once a maintainer adds that label, which reviews it again. A pull request may use 500,000 model tokens unless `[budget] pr_tokens` is set, and one installation may have at most 20 pull requests waiting (`BYLAW_APP_MAX_PENDING_PER_INSTALLATION`).
- In the app, `.bylaw.toml` on the default branch of the organisation's `.github` repository sets defaults, and a repository's base branch `.bylaw.toml` overrides them key by key; a table such as `[jira]` counts as one key. A pull request can change neither (ADR 0004).
- In the app, model keys and tracker tokens are per installation, from `BYLAW_INSTALLATION_<id>_<NAME>` variables or a mounted directory with one file per secret. A server-wide key is never used for an installation. Where a tracker token may go comes from the store too (`JIRA_URL`, `AZURE_DEVOPS_ORGANIZATION`): a repository's `[jira] url` or `[azure_boards] organization` that differs is not read and the token is not sent, so a repository cannot point the installation's credentials at a host it picks.
- In the app, only the app's own bot login carries bylaw's state: a summary or a fingerprint marker from any other bot, or a summary written by a person, is ignored and never edited (ADR 0017, the alternative ADR 0008 named).
- `docs/app/manifest.json` registers the app with four permissions, pull requests write and contents, issues and metadata read, and the `pull_request` event only; `docs/app/register.html` sends it to GitHub from a local page. A test keeps the manifest equal to the permissions the server's tokens ask for.
- A container image for the app (`Dockerfile`): slim, non-root, built from the lock file, with a health check written in Python because the slim image has no curl or wget. [docs/app/deploy.md](docs/app/deploy.md) covers registration, running, installing, organisation defaults and keys. `tools/app_smoke.py` runs the app end to end against a fake GitHub, as a process or as the image, and checks that Docker reports it healthy.
- `bylaw mcp` runs an MCP server on standard input and output, so any agent that speaks MCP can review with bylaw and its own model, no API key and no shell needed. The tools are the skill's flow: `context`, `brief`, `schema`, `validate` and `preview`, all read-only. Each takes its target as arguments, `repo` and `pr` or a local `base` and `path`, and `validate` and `preview` check a result against the context the last brief read, so a push in between cannot move the lines. Local reviews read only repositories inside the server's working directory or the `--root` directories it was given. The MCP SDK is an optional extra, `bylaw[mcp]`, so the Action and the CLI do not install it (ADR 0019).
- `bylaw mcp --allow-post` adds a `post` tool that publishes a validated result to a pull request, as `bylaw post --pr` does, with `.bylaw.toml` read from the base branch. Without the flag the tool is not listed and cannot be called (ADR 0019).
- A local `--base` that starts with `-` is refused instead of reaching git as an option.

## 0.4.0 - 2026-10-18

- Line numbers in the brief and in validation count only newlines, as GitHub does, so a form feed or a U+2028 in a rule file, an ADR or an `.editorconfig` no longer shifts the lines after it.
- The evaluation set has 57 cases: two new ones in `py-ledger`, a project with a superseded, an accepted and a proposed ADR. One change opens its own database connection against the accepted decision and is labelled with that decision's line; the other does the same work through the store and is clean.
- Superseded, deprecated, rejected and proposed ADRs are not decisions. The status is read clause by clause with links removed, and the last clause that names a status decides: `Accepted, superseded by 0012` counts as superseded, while `Accepted. Supersedes 0003`, an adr-tools link such as `Supersedes [3. Keep the deprecated logger](...)` and `Not accepted` are read as what they say. Implemented, adopted and decided count as accepted, and a status history counts its last entry. A proposal is still under discussion, so a change is not held to it (ADR 0016).
- Changes are checked against accepted ADRs. The brief has a `decisions` block with each accepted ADR's title, status and decision section, numbered with the file's own lines, newest first and capped at 2,000 characters per ADR and 12,000 in all; the summary notes what was cut or left out and lists the ADRs among the rule sources. A change that goes against a decision gets a `rule` finding citing `docs/adr/<file>.md:<line>`, and validation keeps the citation only for a line the reviewer was shown. A changed ADR on the base branch forces a full review (ADR 0016).
- ADRs are read as decisions, not specs. `adr_globs` in `.bylaw.toml` (default `docs/adr/**`, `doc/adr/**` and `docs/decisions/**`) says where they live, subdirectories included; bylaw reads the newest 40 from the base branch in one GraphQL query, skipping READMEs, indexes and templates, and keeps the accepted ones, whether the status is a `Status:` line, a table row, a `## Status` section or MADR front matter. An ADR under a package binds only that package. One note names the ADRs bylaw could not read, another an ADR the pull request links but is not checked against, and an ADR the pull request adds is noted as not yet a decision. `docs/adr/**` left the default `spec_globs`, and a file matching `adr_globs` is never a requirement, even when an older configuration still lists it as a spec, so an ADR is not counted twice (ADR 0016).
- Jira Cloud issues as requirements. A pull request that names an issue such as `PROJ-123` in its title, body or commits gets that issue's acceptance criteria in its summary, from a checklist or an "Acceptance criteria" section in the description or from a criteria field you name. It is an opt-in: a `[jira]` table in `.bylaw.toml` with the site and the allowed projects, and `JIRA_EMAIL` with `JIRA_API_TOKEN` in the environment (the Action's `jira-email` and `jira-api-token` inputs).
- Azure Boards work items as requirements. `AB#123` in a pull request's title, body or commits brings in that work item's title, description and Acceptance Criteria field. It needs an `[azure_boards]` table in `.bylaw.toml` with the organisation and the allowed projects, and `AZURE_DEVOPS_TOKEN` (the Action's `azure-devops-token` input). A work item in a project that is not listed is left out.
- Linear issues as requirements. An identifier such as `ENG-42` from a team listed under `[linear] teams` brings in that issue's title and Markdown description, with `LINEAR_API_KEY` in the environment (the Action's `linear-api-key` input). Only keys of listed projects and teams count as references, so `UTF-8` or `SHA-256` in a description never does.
- `quote_trackers = false` in `.bylaw.toml` keeps work item text out of the summary comment: for Jira, Azure Boards and Linear requirements it shows only the criterion keys, their status and where they are met, so a public pull request does not quote a private tracker (ADR 0014).
- Setup for each tracker, the Action inputs and what a left-out work item's note means: [docs/trackers.md](docs/trackers.md).
- Work items are read only for pull requests by owners, members and collaborators; for anyone else a note says they were not read. `trackers_for_all_authors = true` reads them for every author. The brief marks a work item kept out of quotes `Quotable: no` and tells the reviewer to name it by its labels only (ADR 0014).
- Tracker text keeps its criteria in more shapes: a code block at the start of a Jira list item no longer hides the criteria after it, HTML `<pre>` blocks and code fences in a criteria field are not read as criteria, table rows read as one line so a Given/When/Then table is a scenario, and a list item continued after a line break or a second paragraph stays one criterion.
- Keys in HTML comments, such as a pull request template's examples, are not work item references, and only ASCII digits make a key.
- A work item that does not exist and one outside the allow list get the same note, so notes do not reveal which keys exist elsewhere. A tracker token an HTTP header cannot carry is a note instead of a failed run.
- A `.bylaw.toml` error never repeats the rejected value, so a token pasted into the file stays out of the log; the message says to rotate it.
- Quoted prose in comments cannot mention people: a zero-width space follows every `@` in text from issues, work items, specs and the model. Code spans are left as written.
- `bylaw eval snapshot` freezes a public pull request into a real evaluation case: the base and head of the files it touches at the commit a review comment was made on, the rule and spec files bylaw reads, the linked issue and the project's licence. Runs on a snapshot use local git only and never read GitHub (ADR 0015).
- `bylaw eval score` reports real pull requests in their own sections, apart from the planted numbers. Real cases that two people have not labelled yet are reported as provisional.
- The real set: 25 pull requests from 15 permissively licensed projects, frozen in `eval/real/` with first-pass labels that two people still need to replace.

## 0.3.0 - 2026-10-18

- Monorepos: a package's own `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` and linter configuration now apply to the files changed under it, next to the root rules. For each changed file and each of those names, the nearest one above it on the base branch is read; directories without changed files are not read. Ruff's `.ruff.toml`, `ruff.toml` and `pyproject.toml` count as one name, in Ruff's order. `.github/CONTRIBUTING.md` and `docs/CONTRIBUTING.md` stay rules for the whole repository. The brief groups the rules by directory, names the changed files each group covers, and tells the reviewer that the nearest directory wins (ADR 0013).
- Validation accepts a rule line from a package's own rule files as evidence, and drops a finding that cites a rule of another package than the file it is on.
- Linter configuration is read as rule ids, without running anything: Ruff's selected and ignored codes and per-file ignores (`ruff.toml`, `.ruff.toml`, `pyproject.toml`), following `extend` on the base branch, ESLint rules and overrides from `.eslintrc.json` and `.eslintrc.yml`, golangci-lint's enabled linters (v1 and v2 files), and .NET `dotnet_diagnostic` severities from `.editorconfig` and `.globalconfig`. What names no ids, such as an ESLint `extends`, a golangci-lint preset, a .NET category severity or the analysis level, is noted in the brief. ESLint configs written in JavaScript stay text. A file that does not parse is noted in the summary. YAML is read with `ruamel.yaml`'s safe loader, a new dependency.
- A finding can cite a linter rule id as evidence, written `<tool>:<id>` (`ruff:S608`, `eslint:no-console`, `golangci-lint:gosec`, `dotnet:CA2100`). The brief lists the ids each configuration enables. Validation drops a finding whose id the configuration governing its file turns off, or does not turn on when bylaw read all of that configuration; under an `extends` or another setting bylaw could not read, an unlisted id is kept. Only configurations for the file's language count, and for Ruff only the nearest one.
- The evaluation set has 55 cases: five new ones in `py-mono`, a monorepo whose two packages have conflicting `AGENTS.md` rules and their own Ruff configurations, two of them labelled with a rule id citation.

## 0.2.0 - 2026-10-18

- Incremental review: on a new push, the model sees only the files whose change differs from the last run, and the unchanged files keep their earlier findings. A criterion that was met stays met while the files it was met in are unchanged. `incremental = false` in `.bylaw.toml` turns it off (ADR 0012).
- A token budget per pull request: `[budget] pr_tokens` in `.bylaw.toml`. Once a pull request has used it, bylaw's own checks still run and the earlier model review stands.
- The summary's footer gives the model tokens of the run and of the pull request.
- When the model review does not run (no key, an error, or the budget), the earlier model findings stand instead of being resolved as fixed.
- The Claude Code and Codex plugin moved to `plugin/`, so plugin directories scan only the files users install. The skill now always runs the bylaw release from PyPI that it names. Existing installs pick up the new path from the marketplace on their next update.
- A moved file that GitHub sends without a blob sha, and whose old path is missing from the base, now gets the binary file note instead of counting as an unchanged move.
- A GraphQL error while reading the older replies of a long review thread no longer ends the run. The thread is read without them and the summary says so. A rate limit still stops the run.
- Validation keeps two different problems of the same category on the same lines, such as a shell injection and a path traversal on one line. Only a finding with the same message as another is dropped as a duplicate.

## 0.1.0 - 2026-10-16

First release.

### Added

- Context collection for a pull request or a local branch: diff, rules from the base branch (`.editorconfig`, linter configs, `CONTRIBUTING.md`, `AGENTS.md`), issues the change closes and specs it links, with their acceptance criteria.
- Deterministic `.editorconfig` checks.
- Model review through Anthropic or OpenAI with a strict output schema, and validation of every finding before posting.
- Inline comments and one summary comment with the requirement checklist; re-runs update instead of repeating, and resolve fixed threads.
- GitHub Action, with recipes for `pull_request` and `pull_request_target`.
- Claude Code and Codex plugins sharing one skill, so the host model reviews without an API key.
- Inferred acceptance criteria for issues and specs written as prose, and maintainers' issue comments as part of the requirement.
- `bylaw eval`: 50 labelled pull requests in four languages, a resumable runner and a scorer.
